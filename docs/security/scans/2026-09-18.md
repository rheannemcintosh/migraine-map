## Findings

### F1. Email verification is never enforced (Medium)

Fortify's email verification feature is switched on, the verification
routes and pages exist, and every data route sits behind the `verified`
middleware. But that middleware only acts on users whose model implements
`MustVerifyEmail`, and the `User` model has that import commented out
(the starter-kit default). The check is therefore a no-op.

**Evidence.** A throwaway Pest test signed in as
`User::factory()->unverified()` and requested the dashboard: HTTP 200. The
profile page also reports `mustVerifyEmail: false`, so the UI never
prompts either.

**Impact.** Anyone who can reach the registration page can sign up with an
address they do not control, use the app in full, and block the real owner
of that address from ever registering. Password reset emails and any future
notifications would go to an address nobody has proved they own.
Mitigated today by Easy Auth in front of production.

**Follow-up.** MM-46.

### F2. CSV export allows spreadsheet formula injection (Low)

`App\Exports\MigraineCsv` writes medication names into the export
verbatim through `fputcsv(..., escape: '')`. Names are free text up to 255
characters. A name beginning with `=`, `+`, `-`, `@`, tab or carriage
return is interpreted as a formula by Excel, Google Sheets and LibreOffice.

**Evidence.** A throwaway test created an ad hoc medication named
`=HYPERLINK("http://evil.example")`, recorded an intake, and generated an
export: the string appears unchanged in the CSV.

**Impact.** Only the user can name their own medications, so this is not a
way to attack the user. It is a way for the file to misbehave on the
machine of whoever the user shares it with, typically a clinician, and a
compliance point for health data exports. Low because the attacker and
victim are both chosen by the data owner.

**Follow-up.** MM-47.

### F3. Deploy workflow uses mutable action tags (Low)

`.github/workflows/deploy.yml` references all six of its actions by
version tag (`actions/checkout@v7`, `docker/login-action@v4`,
`docker/setup-buildx-action@v4`, `docker/build-push-action@v7`,
`azure/login@v3`, `azure/cli@v3`). `tests.yml` already pins to commit
SHAs. Semgrep flagged each of the six.

**Impact.** A moved tag runs attacker-chosen code inside the job that holds
`packages: write` and the Azure OIDC identity, which is the highest-value
job in the repository. Dependabot keeps the tags current but cannot protect
against a tag being repointed.

**Follow-up.** MM-48.

### F4. No Content-Security-Policy header (Low)

The production image (`serversideup/php:8.4-fpm-nginx`) sends
`X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin` and
`Strict-Transport-Security`, and hides server and PHP versions. It does not
send a Content-Security-Policy, and neither does the application.

**Impact.** No injection was found (see the manual review), so this is a
missing defence in depth rather than an exposed weakness. The root Blade
layout has an inline script, so a policy needs a nonce; Laravel's Vite
integration supports that.

**Follow-up.** MM-49.

## Manual review

Automated tools cannot tell whose data a query returns, so the application
code was read with the following checklist. Everything below was checked
and found in order unless listed as a finding above.

**Authorisation.**
- Every data route is behind `auth` and `verified` (see F1 for the latter).
- Every read query starts from `$request->user()->...()`, so it is scoped
  to the signed-in user.
- Every update and delete on a bound model checks ownership:
  `UpdateMigraineScoreRequest` and `UpdateMedicationRequest` in
  `authorize()`, and `abort_unless($request->user()->is(...))` in
  `CalendarController::destroy`, `MedicationConfirmationController::destroy`
  and `MigraineExportController::download`.
- Foreign keys supplied by the client are validated against the user's own
  rows: `medications.*.id` must be one of the user's active ad hoc
  medications, and `medication_schedule_id` must belong to one of the
  user's medications. Ingredients and schedules are only ever written
  through the parent medication.

**Input handling.**
- All writes go through Form Requests with explicit rules; enums are
  validated with `Rule::enum`; dates use `date_format`.
- Mass assignment is limited by `#[Fillable]` on every model, and
  `user_id` is never fillable.
- No raw SQL anywhere in `app/`. The one `DB::raw('0')` is a constant in a
  migration.
- The only frontend HTML sink is the QR code (I6). No `eval`, no
  `innerHTML`. The only `window.location.assign` uses a server-generated
  route.
- No open redirects: every redirect targets a named route or `back()`.

**Authentication and sessions.**
- Fortify with registration, password reset, email verification (F1),
  confirmable two-factor and passkeys, all with password confirmation.
- Login limited to 5 per minute per email and IP; two-factor to 5 per
  minute; passkeys to 10 per minute; password change to 6 per minute.
- Production password rule: 12+ characters, mixed case, numbers, symbols,
  and not in a known breach.
- Security settings page requires recent password confirmation. Account
  deletion requires the current password.
- Sessions: HTTP-only, `SameSite=Lax`, secure cookie and cookie driver in
  production. `SESSION_ENCRYPT` is off but the cookie driver encrypts
  regardless.

**Data lifecycle.**
- Account deletion cascades to every health table. Verified with a
  throwaway test that created a medication, ingredient, schedule, intake,
  confirmation, score and export, deleted the account through the real
  endpoint, and confirmed every table was empty. Two tables reach the user
  only via their medication rather than directly, which is why they lack a
  cascade on `user_id` (SQL Server rejects multiple cascade paths), but the
  outcome is the same.
- Exports store only their parameters and regenerate the CSV on each
  download; nothing is written to disk.

**Configuration and deployment.**
- `.env` is git-ignored and was never committed (gitleaks, full history).
- `.dockerignore` excludes `.env*`, `.git`, tests and docs, so the
  production image carries no secrets or history. The build stage deletes
  its throwaway `.env` too.
- Production runs `APP_DEBUG=false`, `APP_ENV=production`, logs to stderr,
  `DB_TRUST_SERVER_CERTIFICATE=false`, and takes `APP_KEY` and
  `DB_PASSWORD` from Container Apps secret references.
- `DB::prohibitDestructiveCommands()` is on in production, which matters
  because the container runs migrations on start.
- The runtime container runs as `www-data`. nginx has `server_tokens off`
  and PHP has `expose_php = Off`.
- CI: `persist-credentials: false` on checkout, OIDC to Azure (no stored
  cloud secrets), minimum `permissions`, tests workflow SHA-pinned (F3 for
  deploy), Dependabot on actions weekly.
- `/up` health endpoint and `/.well-known/passkey-endpoints` are public by
  design and return nothing sensitive.

## Repeating this scan

Run `./scripts/security-scan.sh` and compare its output with the summary
table above; then repeat the manual review checklist. The tool images are
pulled at `latest`, so rule sets and advisory databases will be newer than
this run. If Semgrep reports a 404 for a ruleset, remove or replace it in
the script before trusting a clean result, because a failed ruleset means
nothing was scanned.
